## Failure 1 — "Conversations fetched: 0" (empty episode)

### Root cause: UTC timestamp parsed as local time

The Tap worker (`workers/tap-gateway/src/index.ts` → `handleApiConversation`) stores
timestamps with SQLite `datetime('now')`, which is **UTC**, serialized as
`YYYY-MM-DD HH:MM:SS` with **no timezone marker**.

The pipeline (`src/generate-episode.ts` → `fetchTapHistory`) parsed those strings with
`new Date(line.timestamp)`. Without a timezone suffix, Node treats the string as
**local time** (America/Anchorage, UTC-8). Every line was shifted **+8 hours** forward:

- A line logged at `2026-08-17 06:15:43 UTC` (22:15 AKDT) parsed as
  `2026-08-17 06:15:43 AKDT` = `2026-08-17 14:15:43 UTC`.
- The episode window was `[cutoff, targetDate]` = `[2026-08-16 07:59:59Z, 2026-08-17 07:59:59Z]`.
- The shifted line (`14:15:43Z`) landed **after** `targetDate` → filtered out.

Every line from the past day landed outside the window → **0 conversations fetched**,
and the episode rendered empty (only CSS classes, no `.tap-line` content).

### Why now (why past episodes worked)

The bug was latent: lines from earlier in the local day could still pass the window
after the +8h shift. This night, all recent bar activity fell in the shifted-out band.
Verified by reproduction: the exact pipeline filter yields **0 lines**; with UTC
parsing it yields **200 lines**.

### Secondary issue: fetch limit

`fetchRoomConversation` used the API default `limit=50`. The API supports `?limit=`
up to 200 (`handleApiConversation`: `Math.min(parseInt(limit ?? "50"), 200)`).
`bar-rail` had ≥200 recent lines, so the default truncated history.

### Fix (committed)

`src/generate-episode.ts`:
1. Added `parseTapTimestamp()` helper — normalizes `YYYY-MM-DD HH:MM:SS` to
   `YYYY-MM-DDTHH:MM:SSZ` (explicit UTC) before `new Date()`.
   Used in both the 24h filter and the sort.
2. Fetch now requests `?limit=200` (API max) so active rooms aren't truncated.

Verified: `fetchTapHistory('2026-08-16')` returns **200 lines**; `selectBest` picks 10.

### The Tap source itself: no drift

- `https://the-tap.casey-digennaro.workers.dev/api` — live, HTTP 200, no auth needed.
- `/api/rooms` returns exactly the 11 room IDs hardcoded in the pipeline.
- Room activity this window: `bar-rail` (200 lines) and `officers-mess` (32 lines,
  older). Other rooms currently 0 lines — normal, not an error.

## Failure 2 — Deploy ETIMEDOUT at 10170/11219 files

### Root cause: 60-second timeout vs ~11k-file / ~2.7 GB tree

`src/pipeline.ts` Phase 6 ran:
`execFileSync('wrangler', ['pages','deploy',...], { timeout: 60000 })`

The `ai-writings` deploy tree has grown to **~11,200 files / ~2.7 GB** (music, radio
theater, podcasts, episodes, images). Uploading takes ~4 minutes (measured: 230.66s
for the successful run). The 60s cap killed wrangler mid-upload every time.

**Consequence:** the last successful deploy was **2026-08-13** (3 days earlier).
`2026-08-15` was also never deployed — the live site served the SPA index page for
both missing episode URLs (Cloudflare Pages SPA fallback returns the root
`index.html`, which is why the "episode" looked 200 but was 4.3 MB of index).

### Fix (committed)

`src/pipeline.ts`:
- Deploy timeout raised `60000` → `900000` (15 min).

Retried with wrangler 4.118.0 (unchanged) — succeeded:
`✨ Success! Uploaded 1058 files (10177 already uploaded) (230.66 sec)`.
No need for `npx wrangler@latest`.

file was moved to `site/fleet-radio.html` in the Aug 2026 reorganization

on the index page.

### 2. Broken episode images on every deployed episode

Episode templates reference `/images/01-boat-at-dusk.jpg` etc., but those default
images lived in `music/images/`. The SPA fallback served the 4.3 MB index HTML as
the "image" (200 + text/html). 

**Fix:** copied the 8 default images from `music/images/` → `images/` in
`ai-writings`. Verified live: `images/01-boat-at-dusk.jpg` now returns
`200, 637893 bytes, image/jpeg`.
